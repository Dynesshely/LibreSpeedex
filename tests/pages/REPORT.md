# Pages check — my-results.html and results/admin.html

Everything here is scratch: a static file server plus stubs for the two PHP
endpoints, so the two new pages could be rendered with realistic data while the
real PHP is written in parallel. Nothing outside `tests/pages/` is
generated by this directory; the pages, stylesheets and scripts it exercises are
the real deliverables.

## Stub commands

The stub is also the static server: it serves the repository root and answers
`/results/mine.php` and `/results/admin_api.php` from one in-memory fixture
(240 rows, 35 of them owned by the records-page client id `b3f1a2c4d5e6f7a8`).

```sh
# app, with the admin password configured ("librespeed")
node tests/pages/stub-server.js 18210

# the "admin is not configured" gate (configured:false)
ADMIN_CONFIGURED=0 node tests/pages/stub-server.js 18211

# the 403 bad_csrf path (the stub rejects the first state changing call)
STALE_CSRF=1 node tests/pages/stub-server.js 18211

# compile the utilities from the repo's own tailwind.config.js; the stub serves
# this file in place of frontend/styling/tailwind.css. It is byte-identical to the
# checked-in bundle as of this pass (see "Tailwind" below), so the screenshots
# show exactly what a normal page load shows.
npx tailwindcss -c tailwind.config.js -i frontend/styling/tailwind.src.css \
  -o tests/pages/tailwind.offline.css --minify
```

Verification scripts (all on 18210 unless noted):

```sh
node tests/pages/shot.js         # screenshots + page/console error capture
node tests/pages/probe.js        # layout metrics at 1300 and 390
node tests/pages/no-id-probe.js  # no-id / rate-limited request counting
node tests/pages/detail-probe.js # detail snapshot at 2x
node tests/pages/state-probe.js  # 401 fallback gate contents
node tests/pages/csrf-probe.js   # needs STALE_CSRF=1 on 18211
```

`shot.js` ends with a real "purge everything", which empties the fixture, so the
stub has to be restarted before another script runs. Chromium is launched by
path (`~/.cache/ms-playwright/chromium_headless_shell-1234/...`) because the
repo's playwright expects revision 1217 and that is what the machine has.

## Verification results

Layout metrics (from `probe.js`):

| page / width | root font | main | records frame (client / scroll) | KPI per row | page horizontal scroll |
| --- | --- | --- | --- | --- | --- |
| my-results 1300 | 10px | 960 | 928 / 928 | 4 | none |
| my-results 390 | 8px | 390 | 364 / 644 | 2 (via the page's ≤800px rule) | none |
| admin 1300 | 10px | 1280 | 1248 / 1248 | 8 | none |
| admin 390 | 8px | 390 | 364 / 880 | 3 | none |

So at both widths the *page* never scrolls sideways; only the table inside its
bordered frame does, which is the intended behaviour on a phone.

Behaviour probes:

* **No local id** — `no-id-probe.js` counts `0` requests to `results/mine.php`
  when `localStorage["librespeedex.clientId"]` is missing, and the page shows the
  friendly empty state instead (`my-results-empty-1300.png`).
* **Rate limited** — exactly `1` request for an id the stub answers `429` with;
  no retry loop, the retry is a button.
* **401** — `state-probe.js`: after clearing the cookie and paging, the gate comes
  back with `note is-warn`, text "The session ended. Log in again to continue.",
  the login form visible again and the header back to "not logged in".
* **403 bad_csrf** — `csrf-probe.js` against `STALE_CSRF=1`: the delete is
  replayed once after re-reading `op=session` and succeeds —
  `showing 1–50 of 240` → `showing 1–50 of 239`, note "record deleted 1 row
  removed.", no page errors.
* **Delete confirm** — the confirm row names the record
  ("Delete test #4000 recorded 2026-10-04 02:55:46 from 10.0.21.135? The server
  will not keep a copy."); confirming removes exactly one row, cancelling leaves
  the total at 240.
* **Purge** — both blocks refuse an untyped confirmation and say what to type;
  purge-all then reports "239 records deleted."
* **Export** — `#export` href after `q=Fibre House`:
  `admin_api.php?op=export&q=Fibre%20House&order=newest`.

Formatting and modes: `npx prettier --check frontend/javascript/mine-results.js
frontend/javascript/admin.js` passes (run on those two files only). Every file
created for this task is mode 644 (pages, stylesheets, scripts and this scratch
directory's contents).

Note on shared files: `index.html`, `frontend/styling/index.css` and
`tailwind.config.js` show mtimes inside this window but were changed by the work
happening in parallel, not by me — the only files I wrote are the seven listed at
the top of this report plus this scratch directory.

One bug found and fixed by these probes, for the record: the buttons inside the
delete confirm row could not resolve the row they belonged to (the confirm row
carried no id), so `delete-confirm` and `delete-cancel` were no-ops. The confirm
row now carries the id as well.

## Tailwind utility classes used, and where they come from

The 45 utility classes in the two HTML files, checked against the bundle
compiled from the repo's `tailwind.config.js` and against the default Tailwind
set:

```
antialiased bg-accent bg-muted/40 flex flex-1 flex-col flex-wrap font-term
gap-3 gap-4 gap-x-8 gap-y-3 gap-y-6 h-[0.9rem] hidden inline-block items-center
justify-between justify-center max-w-[128rem] max-w-[96rem] min-h-screen mt-6
mx-auto normal-case pb-10 pb-6 pt-2 px-6 py-6 relative sm:flex sm:px-12
text-[1.25rem] text-[1.2rem] text-[1.4rem] text-center text-ink text-muted
tracking-label tracking-terminal uppercase w-[0.9rem] w-full z-10
```

**Nothing outside the default set and the project's declared extensions was
invented.** Specifically:

* From the theme in `tailwind.config.js` (declared available in the brief):
  `bg-accent`, `text-ink`, `text-muted`, `bg-muted/40`, `font-term`,
  `tracking-label`, `tracking-terminal`.
* Everything else is default Tailwind, including arbitrary values of default
  utilities: `text-[1.2rem]`, `text-[1.25rem]`, `text-[1.4rem]`,
  `h-[0.9rem]`, `w-[0.9rem]`, `max-w-[96rem]`, `max-w-[128rem]`.
  (`max-w-[128rem]` is only on the admin page, which needs the width for a nine
  column table.)
* `sm:flex` / `sm:px-12` are the default `sm` screen variants, copied from the
  existing header.
* I did not need `alt`, `screen`, `warn`, `bad`, the `shadow-accent*` values or
  the `accent`/`alt` data colours as utilities in the markup: the download /
  upload hues are applied by the component classes (`.v-dl`, `.v-ul`, `.kpi.is-dl`,
  `.kpi.is-ul`) so the markup cannot drift from the palette.

Deliberate avoidance: I named the filter-bar field wrapper `.filter-field`
rather than `.filter`, because `filter` is a Tailwind utility and the utilities
are imported last, so the two would have collided in one class attribute.

The other 59 classes in the markup (`btn*`, `kpi*`, `note*`, `records*`, `panel*`,
`params`, `pager*`, `login-*`, `filters`, `filter-field`, `caret`, `num`, `dim`,
`th-unit`, `trunc*`, `v-dl`, `v-ul`, `console-page`, `section-head`, `sub-head`,
`field*`, `legend`, `log-view`, `maintenance-*`, `row-actions`, `confirm-row`,
`record-actions`, `visually-hidden`, `is-*`) are hand-written component classes
in `records.css` / `mine-index.css` / `admin-index.css`, not Tailwind utilities.
`.legend-swatch`, `.wordmark`, `.crt-led`, `.crt-overlay`, `.crt-pixels`,
`.status-bar`, `.status-cell`, `.status-label`, `.terminal-link`, `.console`,
`.tagline` are reused as-is from `terminal.css` / `main.css` / `crt.css`.

## Open questions

1. **Resolved during the pass, recorded here because it was a real risk.**
   `tailwind.config.js` (updated in parallel) now lists both new pages, and the
   checked-in `frontend/styling/tailwind.css` was rebuilt at the same time:
   `cmp` says it is **byte-identical** to the bundle I compiled from the same
   config (6897 bytes) and that my screenshots were served. So nothing further is
   needed for the utilities to be there. I did not run `npm run css` myself —
   that file is not in my write set — and the only difference a fresh rebuild
   would make today is dropping the now-unused `.filter` utility, since the
   filter bar's wrapper class was renamed to `.filter-field`.
2. **`op=detail` response shape.** The brief says "a single row including `log`".
   The page accepts either `{...row...}` or `{row: {...}}`; the stub returns the
   bare row.
3. **`params` and `ispinfo` types.** Rows may carry these as JSON strings or as
   already-decoded objects. Both are handled (parse, else use as-is, else fall
   back to the raw text), but if the real endpoints guarantee an object the
   parsing code is dead weight.
4. **`total` vs the rows on screen.** `mine.php` returns no aggregates, so the
   records page computes best download / best upload / average ping from the
   rows it has loaded and says so in the unit line ("over 25 loaded") once
   `total` exceeds what is loaded. If a server-side summary is added later, that
   line should go.
5. **Pagination on the records page.** The brief did not ask for it, but the
   endpoint is paginated, so there is a "load older" button and a "showing 1–25
   of 35" line. Nothing is auto-fetched.
6. **Admin `order` values.** Assumed `newest` / `oldest` / `dl` / `ul`, as in the
   brief's example query string. If the backend expects something else for the
   speed orderings, only the `<select>` values and the stub need changing.
7. **Purge confirmation.** "Typed confirmation *or* two-step confirm" — the
   dated purge requires the cutoff date to be typed out, purge-all requires
   `PURGE`. The affected count is only known for purge-all (from `op=stats`);
   the dated purge says so instead of guessing.
8. **`localStorage` key lifetime.** Clearing the id does not touch the server
   data, as asked. There is no way back to those rows from this browser, which
   the armed state says explicitly.
9. **`results/admin.html` is served from `/results/`.** If the webserver in front
   of the real deployment blocks that directory (some setups do), the page needs
   a rule, and the relative paths (`../frontend/...`, `admin_api.php`) depend on
   it staying one level down.
